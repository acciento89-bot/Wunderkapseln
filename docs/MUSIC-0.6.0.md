# Original garden music — 0.6.0

The mobile game adds an original, deterministic 32-second composition: twelve bars at 90 BPM with soft arpeggios and low accompaniment. `ui/music.mjs` synthesizes mono 22050 Hz, 16-bit PCM. `npm run assets` regenerates `assets/music/wonder-garden.wav`; no downloaded recording or external licence is required. The existing fourteen sound effects stay unchanged.

One hook-owned Expo Audio player loops at volume 0.18. A separate persistent Music setting defaults on for existing saves and does not change the Sound effects preference. Foreground loss, campaign dialogs and a paused rescue stop playback. Native audio configuration failures stay cosmetic; stale async setup cannot start playback after pause or disposal. Cleanup pauses the player and lets the hook release its own resource.

Verified: deterministic PCM container, bounded peak and nonzero RMS, silent loop endpoints, independent saved preference and old-save migration, lifecycle policy and async cancellation. These checks establish source behavior and audio data, not audible playback or actual device acceptance. Native Android acceptance is a separate release gate. Browser preview remains an engine/UI preview without the new native music player.

Native acceptance found an Android foreground auto-resume: the SDK restarted the stream while the rescue model and visible Resume button remained paused. The driver now observes the supported `playbackStatusUpdate` event and pauses playback that contradicts its current policy. This uses no React status state or extra game rerenders, requests no recording access, removes the listener on disposal and never releases the hook-owned player. EventEmitter regressions cover native auto-resume, pending/failed configuration and late disposed callbacks. API reference: https://docs.expo.dev/versions/v55.0.0/sdk/audio/ . Fresh native foreground testing remains required for this correction.

A follow-up isolated event-order test found that the initial status guard conflated playback-command bookkeeping with configuration readiness. The guard now tracks successful configuration separately, avoids an unnecessary await on an already configured resume, and allows approved native playback while continuing to block held, muted, or unconfigured playback. The regression failed before the correction and all 303 source checks pass afterward. This is a defensively tested ordering fix; it is not evidence of a second native silence defect.

The earlier native list-return silence diagnosis was a QA-parser error: AudioFlinger reported an active nonzero-gain RESUMING (`r`) track with advancing frames, but the probe accepted only ACTIVE (`A`). The corrected probe accepts both states and requires advancing server frames. Independent native MediaSession data also reported PLAYING with advancing positions. No human audibility claim is made on the audio-disabled emulator. The exact locked expo-audio 55.0.16 Android source was verified against its official npm SHA-512 integrity; its play/pause operations use the main queue synchronously via runBlocking, so an arbitrary queued native pause was not established. A fresh native candidate remains required for final acceptance of the readiness guard.
